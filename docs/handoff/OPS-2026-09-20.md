# Эксплуатация MaestroVPN — что добавлено 20.09.2026 (безотказность)

> Продолжение `INCIDENT-2026-09-19-rqlite.md`. Причина аварии 19.09 — неограниченный рост базы rqlite
> (1.5 ГБ → проверка схемы 118 с → панель не стартовала). Ниже — что сделано, чтобы это не повторялось,
> и как всё проверять.

## 1. Что установлено на S1 (панель)

| Юнит | Расписание | Что делает |
|---|---|---|
| `maestro-rqlite-retention.timer` | ежедневно **01:40 UTC** (+ разброс до 10 мин) | Удаляет из БД rqlite устаревшие строки чанками по 2000: `whitelist_metering_events` старше **14 дней**, `idempotency_requests` старше **7 дней**. Пишет JSON-отчёт в journal. Если размер БД ≥ 600 МБ — дополнительно `VACUUM`. |
| `maestro-rqlite-backup.timer` | ежедневно **02:10 UTC** | Скачивает консистентный снапшот через `/db/backup` (клиентский сертификат S1), gzip в `/var/backups/maestro-rqlite/rqlite-<ts>.sqlite.gz`, хранит **последние 3**. Тест: 369 МБ → 78 МБ, ~31 с. |
| `maestro-panel-watchdog.timer` | каждые **5 минут** | Проверяет `http://127.0.0.1:18910/healthz`. Два провала подряд → `systemctl restart maestro-cdn-controller` + уведомление владельцу в Telegram. Токен и чат: `/etc/maestro-panel-watchdog/notify.env` (600, root). |
| `maestro-flat-charge.timer` | каждые 2 минуты | (был и раньше) списание ГБ из счётчиков всех 4 origin’ов. |

Дополнительно: на S1 замаскированы бесполезные на VPS `fwupd.service`/`fwupd-refresh.service` и выключен
`fwupd-refresh.timer` — теперь `systemctl --failed` пуст (было 2 «красных» юнита).

## 2. Как проверить, что всё живо (быстрый чек-лист)
```bash
# на S1
systemctl --failed --no-legend | wc -l                      # ждём 0
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18910/healthz        # 200
systemctl list-timers 'maestro-*' --no-pager | head          # все таймеры с NEXT
journalctl -u maestro-rqlite-retention -n 5 --no-pager       # последний отчёт ретенции
journalctl -u maestro-rqlite-backup -n 3 --no-pager           # последний бэкап
tail -n 5 /var/log/maestro-panel-watchdog.log                 # только FAIL/рестарты
# размер базы и задержка rqlite (strong)
# (см. INCIDENT-2026-09-19-rqlite.md § «Полезные факты»)
```

## 3. Пороги и тревоги
- БД > 600 МБ → ретенция запускает `VACUUM`; БД > 800 МБ — повод разобраться, что пишет так много.
- Панель не отвечает 10 минут → сторож перезапускает; если и после этого нет — владельцу придёт уведомление.
- rqlite strong > 2 с или панель в цикле `schema unavailable` → смотреть `INCIDENT-2026-09-19-rqlite.md`.

## 4. Открытый вопрос: `/account/whitelist-runtime` → 503
Приложение (все клиенты) периодически опрашивает `GET /account/whitelist-runtime` и получает
`503 {"error":"unavailable"}`. Причина не в сбое: в конфиге панели выключен **whitelist-сайдкар**
(`MAESTRO_WHITELIST_SIDECAR_ENABLE=0`), поэтому `WhiteListPublicationSource = nil`, и нативный runtime-вид
честно отвечает «недоступно». Этот механизм — старая схема «exit-маршрутов через сайдкар-агентов»,
которую заменил flat-CDN (`/cdn-sub/` + метры origin’ов). Клиенты при этом работают: подписка `/cdn-sub/`
отдаётся и трафик идёт.
Варианты (нужно решение владельца):
1. оставить как есть (приложение само уходит на `/cdn-sub/`);
2. включить сайдкар обратно (`MAESTRO_WHITELIST_SIDECAR_ENABLE=1` + агенты на узлах) — вернёт старый контур,
   который 18.09 перегружал панель;
3. реализовать `WhiteListNativeRuntime` поверх flat-CDN-нод (профили из `flat-cdn-node.json` + гейт по ГБ) —
   тогда приложение получит «белые списки» нативно, без 503 и без сайдкара. Это доработка кода панели.
