## Полезное из Selectel-гайда

Автор разделяет origin и панель по разным доменам, выпускает сертификаты, ставит Nginx и сайт-заглушку, а Xray слушает только loopback. Для Selectel создаётся статический CDN-ресурс с HTTPS-origin `:443`, отключаются кеширование и gzip, увеличиваются таймауты, разрешаются `POST` и `DELETE`. VLESS/XHTTP работает в `packet-up`, uplink отправляется методом `DELETE`. Результат проверяется импортом в INCY, фактическим подключением и внешним тестом операторов.

Переносимые принципы: отдельный origin, точный XHTTP path, закрытый Xray inbound за reverse proxy, отключённые преобразования контента, проверка реальным клиентом. Непереносимые значения: HTTP-метод `DELETE`, разрешение `POST/DELETE`, таймаут `30` и конкретные extra-параметры. Они зависят от Selectel и не являются универсальным рецептом.

## Что показали материалы про Yandex

Короткое видео `3WuqJE4aJw0` описывает каскад «клиент → Yandex Cloud VM → зарубежный exit», но не показывает CDN-resource, точные XHTTP-параметры, версии ядра, методы или результаты по разным операторам. Утверждение, что любой IP Yandex Cloud находится в белом списке, не доказано и противоречит полевым сообщениям о различиях между подсетями, регионами и базовыми станциями. Использовать это видео как настройку нельзя.

Обзор `lXp0yCtwJpA` рекламирует автоматический установщик и перечисляет Yandex/VK/Timeweb/Beeline. Технических параметров в видео нет. Текущий публичный README v3.0 полезнее: он явно разделяет ветки по CDN, для Yandex указывает отдельный origin и возможность HTTPS до origin, для Selectel — `DELETE/POST` и увеличенные таймауты. Исходник продаваемого установщика в публичном репозитории отсутствует, поэтому его безопасность и точную реализацию проверить нельзя.

Официальные материалы Yandex подтверждают: базовые разрешённые методы — `GET`, `HEAD`, `OPTIONS`; дополнительные методы требуют отдельной поддержки. Изменения настроек могут распространяться до 15 минут. CDN позволяет выбрать HTTP/HTTPS до origin, управлять Host/SNI, кешированием, gzip, сегментацией, логами и мониторингом. Метрики дают разбивку по методу, статусу, времени edge/origin и трафику.

## Текущий ресурс MaestroVPN

Read-only просмотр консоли 12.09.2026 подтвердил:

- origin group — существующая commercial ingress на S4;
- протокол CDN → origin — HTTP;
- Host передаётся как у клиента;
- клиентский TLS-сертификат выпущен, HTTP перенаправляется на HTTPS;
- разрешены `GET`, `HEAD`, `OPTIONS`;
- кеш CDN и браузера выключен;
- gzip и сегментация выключены;
- локационных правил нет;
- shielding и выгрузка raw-логов не активированы;
- в просмотренных формах нет настройки response idle timeout.

HTTP между Yandex и ingress не равен открытому VPN payload: действующий VLESS использует ML-KEM encryption внутри XHTTP. Однако TLS до origin дополнительно скрыл бы HTTP metadata на этом участке; менять origin-протокол без отдельного canary нельзя, потому что нужны согласованные сертификат, SNI и ingress listener.

## Вывод для нашей схемы

Наш проверенный Yandex-профиль должен сохранять: VLESS ML-KEM, XHTTP `packet-up`, `GET` uplink с данными в body, session/sequence в query, точный статический path, TLS к CDN hostname, правильные Host/SNI и отключённые кеш/gzip/segmentation. Selectel-параметры `DELETE/POST` к Yandex не применять.

Наличие пинга или профиля не доказывает стабильность. Для изменения транспорта достаточно одного разрешённого canary-сценария: начальный запрос, передача данных, новый запрос после простоя и проверка целостности открытого ответа. Уже установленный production не менять по результатам видео: INCY/HAPP подтверждены владельцем как работающие.

Открытый вопрос Yandex остаётся прежним: длительный HTTP/2 response без downstream DATA обрывался около 60 секунд, тогда как loopback без CDN завершал 127 секунд. Видео не содержит решения этого ограничения. `noSSEHeader`, XMUX и случайное увеличение таймаутов повторять без новых оснований нельзя.
