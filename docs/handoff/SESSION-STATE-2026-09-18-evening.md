## Ошибка этой сессии (важно)
Попытка поднять окно лизы до 180 с только в панели и в агенте заклинила агента:
runtime (`internal/runtimefence/runtime.go: maxLease = 60 s`, вшит в бинарь xray)
и `internal/xrayclient/lease.go (managedLeaseWindow = 60 s)` остались на 60 с.
Невыполнимая pending-лиза зависла навсегда (см. ниже), CDN лёг на ~15 минут.
Вывод: **окно лизы меняется только целиком**: agent + xrayclient + runtimefence +
панель, с пересборкой и выкатом xray-runtime на S4.

## Баг агента (лечить в коде)
Невыполнимая pending-лиза не сбрасывается: `saveLeaseChallengeLocked` не выдаёт
новый challenge, пока `state.Pending != nil`; запрос с другим хешем отвергается
`ErrConflict`; повтор того же запроса вечно возвращает needs_fresh_nonce.
Система выходит из этого только ручной чисткой состояния
(`managed-lease-state.json`). Сегодня чистили дважды (бэкапы
`/root/lease-state-before-pending-clear*.json` на S4).
Правильно: при невыполнимой pending (смена boot/config/просроченный deadline)
сбрасывать её и позволять новый grant.

## Плоский CDN-стек (S4:18081): рекомендация
Плоский стек (canary, путь /static/main/video/segment.ts/<hash>, порт 18081) уже
поднят на S4 и не зависит от managed-lease. Но:
* он не даёт per-user учёт и лимиты (байтовые потолки/white-list) — продукт «CDN по
  ГБ» превращается в открытый канал для всех, у кого есть ссылка;
* панель/бот продают CDN как отдельный пакет ГБ — без managed-слоя нечего списывать.
Рекомендация: **не убирать managed-схему как основную**, а:
1) добить окно лизы 180 с (полный список мест выше) — это уберёт мигание;
2) держать плоский стек как аварийный профиль (вторая подписка «CDN-резерв»),
   включаемый флагом, с честным предупреждением об отсутствии учёта;
3) вернуться к вопросу «плоский как основной» только после недели наблюдений и
   решения по биллингу.
