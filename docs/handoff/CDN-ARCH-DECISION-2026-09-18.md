# CDN: решение владельца и план (18.09.2026, вечер)

## Решение владельца (принято)
Делаем как у Аконита — **две подписки у клиента**:
1. обычный VPN (как сейчас);
2. CDN отдельной подпиской; в боте клиент покупает ГБ.
CDN работает **только при активной обычной подписке**: истекла обычная — CDN-подписка не
работает (локации не отдаются/не подключаются).

## Что это значит технически
* CDN-узел перестаёт зависеть от managed-lease (никаких use-lease, challenge, white-list
  receipt, byte-admission). Origin — обычный VLESS+XHTTP, клиенты — статические ключи,
  как у плоского canary-стека.
* Панель отдаёт **вторую ссылку-подписку** (только CDN-локации). Гейт: обычная подписка
  active И баланс ГБ > 0. Иначе 403/404 (у клиента CDN-локации исчезают).
* Бот: покупка ГБ + выдача CDN-ссылки/QR + показ остатка.
* Учёт ГБ: считать трафик на плоском узле (Xray stats per-user) коллектором и списывать
  с баланса; при исчерпании — перестать отдавать CDN-подписку/заблокировать UUID.

## Состояние транспорта (важно, до кода)
Плоский стек **работает при прямом подключении к origin** (проверено настоящим Xray
клиентом: 204 через 127.0.0.1:18081). Но через край/ingress аплинк получает **400**:
* клиент → edge (cdn-test.wapmixx.ru:443) → 400 для обоих стеков (flat и commercial);
* клиент → origin nginx (89.125.19.95:28080) → flat 400, при этом прямой заход на
  18081 — 204;
* дамп запроса показал: nginx передаёт аплинк (GET, тело 2.9 КБ) наверх без искажений,
  т.е. дело не в потере тела;
* проба «OPTIONS→POST в nginx» (map по chunk_id + proxy_method) результата не дала;
* в 17:06 UTC тот же commercial-стек через край работал (node-watch 8/8) — значит
  поведение края/цепочки изменилось в районе 17:08 UTC.

Что нужно: проверить в консоли Yandex CDN настройки ресурса (origin, разрешённые методы,
path-правила) — доступ только у владельца. Инструкция владельца

маппинг OPTIONS→POST на origin; в текущем ingress-nginx такого маппинга нет.

## Ошибки и грабли (не повторять)
1. Менять окно лизы только в панели/агенте нельзя: runtime (`runtimefence: maxLease`)
   и `xrayclient: managedLeaseWindow` тоже 60 с — получается заклинившая pending-лиза.
2. Править `config.json` на S4 нельзя без пересчёта digest: агент падает в рестарт-луп
   `relay preflight: runtime config digest mismatch`. Любая правка конфига — только
   через пересборку релиза.
3. У агента нет выхода из невыполнимой pending-лизы (нужен код-фикс: сбрасывать
   pending при смене boot/config).
4. После смены boot xray у агента остаются active-юзеры прошлого boot — они блокируют
   выдачу новых лиз (лечится ручной чисткой state; нужен код-фикс).
