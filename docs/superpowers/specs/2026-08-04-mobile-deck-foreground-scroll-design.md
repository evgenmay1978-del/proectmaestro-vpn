# Mobile Home: движущаяся дека поверх бокового орнамента

**Решение владельца:** 04.08.2026  
**Ветка:** `codex/mobile-deck-layer-order`  
**База:** `codex/mobile-4d-deck`  
**Область:** только мобильный `Home`; TV, backend, VPN-runtime, release и OTA вне задачи.

## 1. Подтверждённый дефект

Один `ScrollState` уже правильно двигает нижнюю Compose-деку и bitmap-слои `console`,
`contacts`, `arc` на одинаковый scroll delta. Ошибка находится не в скорости или геометрии,
а в z-order:

```text
wood → console(scroll) → contacts(scroll) → frame → cartouche → vines →
arc(scroll) → ring
```

Из-за этого резные плиты `Telegram / МАКС / WhatsApp` и нижняя консоль
`Ввести логин / Тест сети / Подключить телефон` при подъёме проходят под неподвижными
боковыми `frame/vines`. Дуга протоколов рисуется после этих слоёв и поэтому правильно идёт
поверх бокового орнамента.

## 2. Утверждённое поведение

Владелец выбрал вариант 1: не менять позиции и прокрутку, а дать всем трём движущимся
relief-слоям то же foreground-поведение, что уже имеет дуга.

Целевой runtime-порядок:

```text
wood → frame → cartouche → vines → console(scroll) → contacts(scroll) →
arc(scroll) → ring
```

- `console`, `contacts` и `arc` остаются одной движущейся декой;
- все три получают прежнее смещение `+25 dp - scrollState.value`;
- все три по-прежнему клипуются сверху по `deckTop = 434 dp`;
- `ring`, живой глаз, картуш и логотип остаются неподвижными;
- позиции, размеры, ссылки, callbacks, hit targets и семантика не меняются;
- существующий tilt/parallax каждого слоя сохраняется;
- Compose-контролы остаются над Canvas и движутся тем же `ScrollState`.

## 3. Реализация

`Mobile4DHome` должен явно отличать runtime render order от порядка упаковки сгенерированного
атласа. Перегенерация 24 WebP не нужна: каждый слой выбирается из manifest по имени, поэтому
порядок его отрисовки можно изменить без изменения пикселей или atlas layout.

`mobile4DHomeReliefLayers` становится единственным runtime-порядком:

1. неподвижные `frame`, `cartouche`, `vines`;
2. движущиеся `console`, `contacts`, `arc`.

`wood` остаётся первым, `ring` — последним. Generated manifest продолжает описывать полный
inventory и порядок упаковки фрагментов; тест больше не должен ошибочно требовать, чтобы этот
технический порядок совпадал с пользовательским runtime z-order. Вместо этого он проверяет
одинаковый набор слоёв и отдельно фиксирует оба порядка.

`ops/phone-screen-sim.py` использует тот же явный runtime render order. Он сначала проверяет
inventory manifest, затем рисует слои в порядке приложения. Второй Canvas, дублирующие слои,
полноэкранная маска и новый арт не добавляются.

## 4. Проверки

1. RED-контракт фиксирует целевой runtime-порядок и должен противоречить текущему
   `console/contacts → frame/cartouche/vines → arc`.
2. JVM-контракт подтверждает:
   - полный runtime-порядок;
   - одинаковый набор runtime и generated слоёв;
   - `console`, `contacts`, `arc` остаются единственными scroll-слоями.
3. Python/self-check симулятора подтверждает отдельные manifest inventory и runtime order.
4. `phone-screen-sim.py` создаёт обычный и прокрученные кадры; при `scroll = 64 dp` и на
   дополнительных диагностических смещениях, где контактный либо нижний ряд пересекает
   боковой орнамент, каждая видимая часть всех трёх контактных плит и консоли композится
   поверх него, как дуга. Элемент, естественно ушедший выше `deckTop`, не обязан оставаться
   видимым.
5. Логотип, глаз и кольцо имеют нулевой scroll delta; верхний clip не меняется.
6. Выполняются GitHub unit tests, GitHub APK compile, simulator/self-check и scope-проверка
   нулевого diff по TV/backend/release/OTA.
7. На Windows не выполняются изменения, тесты, симулятор или сборка. Все дальнейшие операции
   выполняются только в GitHub; тестовый APK — только через GitHub Actions.

## 5. Риски и границы

- Движущиеся плиты будут визуально перекрывать боковую резьбу именно в зоне пересечения — это
  утверждённый результат, совпадающий с поведением дуги.
- `ring` остаётся поверх деки, а `deckTop` не позволяет движущимся слоям попасть на глаз.
- Изменение не затрагивает данные, VPN, навигацию, обновление приложения или TV-ветку.
- Новый арт, изменение atlas-файлов и переразметка элементов не входят в задачу.

## 6. Критерий готовности

На скролле контактный ряд и весь нижний ряд действий идут поверх бокового орнамента с тем же
scroll delta и верхним clip, что дуга; неподвижный герой не сдвигается, тестовые контракты и
симулятор совпадают с runtime, а запрещённые области имеют нулевой diff.
