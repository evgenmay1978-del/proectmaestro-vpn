# Оплаты и функциональная проверка ботов — 11.09.2026

## Запрос и граница
Владелец сообщил об отсутствии сообщения с подтверждением оплаты CDN, затем явно поручил проверить начисление, самостоятельно подтвердить контрольные заявки и проверить остальные функции обоих ботов. Это разрешение на адресные проверки данной задачи, не на автоматический тестовый CI в будущем. Действия с днями, тарифами, блокировкой, удалением, рассылкой и резервным копированием проверялись на отдельных временных SQLite/фиктивной панели и Telegram; реальные соединения в функциональных проверках блокировались. Действующие клиенты для разрушительных проверок не использовались.

## Что воспроизведено и исправлено
1. S2: на контрольном «Я оплатил» update385759167 обрабатывался60486ms; заказ остался created, notified_owners пуст. В интервале не было запроса paid-claim. Потом бот показал общую ошибку. До обращения к платёжному API код ожидал answerCallbackQuery с сетевым таймаутом Telegram. Исправление: служебный ACK ограничен3s и не останавливает действие. В общем aiogram session middleware правило действует только на answerCallbackQuery; ошибки sendMessage НЕ подавляются.
2. При сбое уведомления обычной оплаты S1/S2 повторное нажатие упиралось в уже существующую pending-заявку и не пересылало её. Теперь повторно отправляется тот же номер, новые заявки/дни не создаются. Сообщение о доставке выдаётся после успешной отправки хотя бы одному администратору.
3. S2 новые административные запросы по внешнему /cdn/admin/customer/... получали404: в Nginx были только order-маршруты. Добавлены три exact location для customers, whitelist-balance, whitelist-credit. Все три без Bearer возвращают401. Никакого общего открытого /admin proxy.
4. S2 неверное/нулевое/слишком большое количество дней при создании клиента раньше превращалось в бессрочный доступ. Теперь ввод отклоняется, бессрочно — только при отсутствии поля дней.
5. S1 редактор разрешал цену0, которую покупка затем не принимала. Теперь цена должна быть положительной. Реальные тарифы не менялись.
6. Android-кнопка HAPP ошибочно вела на v2RayTun. Заменена на https://play.google.com/store/apps/details?id=com.happproxy ; имя продукта проверено по официальной странице магазина и happ.su. Новая ссылка также прочитана в реальном сообщении Telegram.
7. S2 отбрасывал UTC-offset и округлял дни вниз. Воспроизведено: expiry через3600s показывал0 дней. Исправлены перевод времени в локальное перед naive-сравнением и округление оставшихся суток вверх; адресная проверка подтверждает сохранение UTC-момента при продлении на30 дней.

## Функциональные проверки
Проверены обработчики покупки/продления обычного VPN, уведомление при недоступности Telegram и повтор той же заявки, подтверждение/отказ, отсутствие повторного продления; CDN ACK/claim/confirm/replay; проверка администратора; ввод ручныхГБ и стабильный ключ повторного подтверждения; привязка и запрет чужой привязки; поиск/списки/карточка; дни/дата/неверная дата; создание/удаление отдельного клиента; блокировка/разблокировка; история/реферальный экран; двусторонний реферальный бонус только за первую оплату; изменение/добавление тарифов и отказ нулевой цены; QR PNG, скриншот оплаты, ZIP-копия тестовых SQLite; рассылка только фиктивным получателям; справка и выбор устройства/приложения для обоих режимов. AppStore карточки HAPP/INCY/Karing и Google Play INCY/HAPP соответствуют приложениям. HEAD Maestro APK, Karing releases и сайта —200.

Исходники воспроизводимых проверок — ops/bot-checks. В процессе исправлены только дефекты fixtures: отсутствующие ADMIN_ID/is_bot/port и column sub_url, которая уже есть в настоящейS2базе; PNG magic проверяется hex. Эти промежуточные падения не являются производственными сбоями. Успешные функции не перезапускались полным CI после каждой правки; повторялись зависимые/изменённые сценарии.

Это проверки функций бота с изолированными зависимостями плюс описанные живые CDN-заявки. Реальные банковские переводы и подключение каждого приложения к каждомуVPN-серверу не выполнялись. Не заявлять абсолютное отсутствие любых ошибок.
