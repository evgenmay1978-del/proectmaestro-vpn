# Рабочий контракт агентов MaestroVPN

**Владелец подтвердил:** 04.08.2026  
**Источник истины:** GitHub  
**Текущая задача:** исправление z-order мобильной Home-деки  
**Рабочая ветка:** `codex/mobile-deck-layer-order`  
**Базовая ветка:** `codex/mobile-4d-deck`

Этот документ обязателен для Codex, Claude и других агентов, продолжающих работу над MaestroVPN. Он дополняет `AGENTS.md` и `CONTEXT_HANDOFF.md`. При расхождении действует более новое явное решение владельца.

## 1. Где выполняется работа

- Постоянным источником истины является GitHub: ветка, коммиты, PR, Actions, artifacts и документы в репозитории.
- Для текущей задачи запрещено изменять проект, собирать APK, запускать Gradle, тесты или симулятор на Windows.
- Локальный Windows-каталог не считается checkpoint и не используется как скрытое продолжение работы.
- Уже разрешённое одноразовое чтение старого worktree применялось только для восстановления точного QA-JPEG; оно не разрешает дальнейшую локальную работу.
- Каждый материальный результат должен быть записан в рабочую ветку и подтверждён удалённым commit SHA.

## 2. Обязательное чтение перед продолжением

Новый агент до любых правок обязан полностью прочитать:

1. `AGENTS.md`;
2. `CONTEXT_HANDOFF.md`, начиная с верхнего LIVE-раздела;
3. этот рабочий контракт;
4. `docs/handoffs/2026-08-04-mobile-deck-layer-order.md`;
5. `docs/superpowers/specs/2026-08-04-mobile-deck-foreground-scroll-design.md`;
6. `docs/superpowers/plans/2026-08-04-mobile-deck-foreground-scroll.md`;
7. `docs/evidence/2026-08-04-owner-home-scroll-proof-qa.svg`.

После чтения агент перепроверяет на GitHub текущий HEAD ветки, PR, последний Actions run и существование artifact. Числа из документов — точка продолжения, а не замена проверки изменяемого внешнего состояния.

## 4. Порядок реализации

- Сначала фиксируются решение, критерии готовности и точный следующий шаг в GitHub.
- Для багфикса применяется TDD: сначала узкий RED-контракт, затем минимальная production-правка, затем GREEN.
- Существующие проверки и скрипты используются раньше создания новых.
- Для этой задачи существующий `ops/phone-screen-sim.py` должен быть исправлен; дублирующий генератор писать нельзя.
- Новый скрипт допустим только для реально повторяющейся операции, которой нет в проекте. Причина, интерфейс запуска и результат должны быть документированы.
- Правки должны быть хирургическими: не менять геометрию, art, atlas, callbacks, hit targets, семантику, VPN-runtime или соседние экраны без нового решения владельца.
- После каждого логического шага создаётся отдельный понятный commit.
- До заявления «готово» проверяются diff, тесты, CI и фактический artifact; зелёная галочка шага upload сама по себе не доказывает наличие APK.

## 5. GitHub Actions и APK

Разрешён только тестовый путь:

- draft PR из `codex/mobile-deck-layer-order` в `codex/mobile-4d-deck`;
- workflow `.github/workflows/android-test.yml`;
- задачи `testOtherDebugUnitTest` и `assembleOtherDebug`;
- artifact `maestrovpn-tv-test-apk`.

После run нужно отдельно записать:

- commit SHA;
- run ID и прямую ссылку;
- conclusion каждой нужной job;
- artifact id и имя;
- ненулевой размер;
- digest;
- результат фактической доступности скачивания.

Запрещено изменять или запускать `.github/workflows/android.yml`, использовать `main`, создавать GitHub Release, production signing, OTA manifest/mirror или публикацию обновления.

## 6. Журнал неудач

Каждая материальная неудача вносится в task handoff до следующей попытки:

- что именно выполнялось;
- наблюдаемый результат;
- подтверждённая или наиболее вероятная причина;
- что уже исключено;
- какой способ нельзя повторять без новых данных;
- точный следующий безопасный шаг.

Нельзя молча повторять один и тот же поиск или действие. Если найден точный объект, его path/SHA/run/artifact/hash фиксируются сразу.

## 7. Поддержание контекста

После каждого материального изменения обновляются task handoff и верхний LIVE-раздел `CONTEXT_HANDOFF.md`:

- ветка и HEAD;
- завершённые шаги;
- изменённые файлы;
- проверки и их честный статус;
- неудачи;
- незавершённое;
- один точный следующий шаг.

Нельзя писать «проверено», если была только проверка исходника; нельзя писать «APK готова», пока artifact не существует и не проверен; нельзя писать «визуально исправлено», пока владелец не проверил тестовую APK на телефоне.

## 8. Барьер релиза и OTA

Все сборки до отдельного разрешения владельца остаются тестовыми.

Единственная фраза, снимающая запрет на подготовку обновления: **«добро на обновление»**.

Любое другое одобрение дизайна, тестовой APK, PR или отдельной правки не разрешает merge в `main`, Release, production workflow или OTA. Даже после этой фразы выпуск выполняется отдельным планом с повторной проверкой версии, signing, manifest, rollback и artifact.

## 9. Текущий утверждённый результат

Для мобильного Home утверждён только следующий runtime z-order:

```text
wood → frame → cartouche → vines → console(scroll) → contacts(scroll) →
arc(scroll) → ring
```

`console`, `contacts` и `arc` используют один прежний scroll delta и прежний верхний clip. Никакие другие визуальные или функциональные изменения в текущую задачу не входят.
